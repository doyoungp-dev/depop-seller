# depop_seller

Semi-automated pipeline for selling second-hand clothes on Depop.
Step 1 (done): sort raw product photos into per-item groups, reviewed by drag and drop.
Step 2 (done): a Sell page whose per-item Depop button opens Depop's listing form with the photos and the description filled in; the human finishes and posts. Descriptions are drafted per item by Claude from photos + a facts line, in the style of `description_style.md`.

## Ownership and commit rules

- Project of GitHub user `doyoungp-dev`, **public** at `github.com/doyoungp-dev/depop_seller` (branch `main`, MIT licence). The history from before publication lives in the private `depop_seller-archive` and never goes public.
- **Everything committed is public - code, docs, tests and commit messages alike.** Nothing personal is ever committed: no photos, no `manifest.csv` (the grouping), no `depop_seller.db`, no `.env`, not the seller's own `description_style.md`, no local paths (a Windows home folder contains a real name), no shop handle, no real listings, no family or friends. All of that lives in the data folder outside the repo (see Data layout). Commit messages describe the software, never whose shop or which batch prompted a change.
- The owner is the **only** author and committer. Never add `Co-Authored-By`, "Generated with Claude", or any AI attribution to commit messages, PR descriptions, or source files. Use the repo-local git identity that is already configured; do not change it.
- Never commit images. `raw_image/`, `sort_image/`, `thumbs/` and the whole `product_image/` tree are gitignored, as is `.claude/` (local Claude Code settings).
- Never commit secrets. `ANTHROPIC_API_KEY` is read from the environment, falling back to `.env` in the data folder (and, for old installs, the app folder). Never read, print, or edit a `.env`; never ask the user to paste a key into chat. Test fixtures use keys that are obviously fake (`sk-ant-test-...`), never the real `sk-ant-api03-` shape, which secret scanners flag.
- **No cloud infrastructure.** Everything runs on the user's own computer (local files, local SQLite). The only network calls are the Anthropic API for photo grouping, Claude Code on the user's subscription for descriptions, and Depop's website in the user's own Chrome, plus (only while the switched-off White Background feature is on) one download of its cut-out model from GitHub, made only after the user confirms it in the Review page. Do not propose or add hosted services, containers or deployment tooling. GitHub Releases are how the app is distributed and updated; that is the one exception, and the app only talks to GitHub when the user presses **Check for updates** or **Update** in Settings - never in the background. No CI: `release` runs the tests locally before anything is published.
- **Releases** are one command: `python -m depop_seller release [X.Y.Z] [--notes ...] [--dry-run]` (`release.py`). It refuses a dirty tree or a branch other than `main`, checks that `gh` is signed in, that `github.com/doyoungp-dev/depop_seller` is public (a private repo's releases are invisible to the app's unauthenticated check) and that this checkout's root commit is the same as `origin/main`'s and a fast-forward of it - **that guard is what keeps the private pre-publication history from ever being pushed to the public repo, even through a tag** - then runs the tests, writes the version into `pyproject.toml`, `depop_seller/__init__.py`, the macOS `Info.plist` and the README's two download buttons (static shields badges with the version in their address - a badge that looked the version up stayed stale on the project page because GitHub caches README images) and commits `Release X.Y.Z`, builds `dist/DepopSeller.zip` from `git ls-files` only (never whatever else sits in the folder) and checks it with `updates.read_update` exactly as installed apps will, builds the Windows installer around that zip (see **Windows installer**), tags `vX.Y.Z`, pushes `main` and the tag, and runs `gh release create` with both files. Default version: the current one if never released, else the next patch; default notes: the commit subjects since the last release, which the Settings page shows as "What's new" - so write commit subjects for sellers. Every step is re-runnable after a failure. `--dry-run` reports every blocker and builds the zip and the installer but commits and publishes nothing. The asset name is stable, so `releases/latest/download/DepopSeller.zip` in the README always serves the newest. Windows and macOS are both supported. Mac users download `DepopSeller-Mac.zip` (the README's Mac button): `build_mac_zip` packs the very same files as `DepopSeller.zip`, checks the file lists match, but names the one folder inside "Depop Seller" - **`DepopSeller.zip` must keep `depop_seller_app/`**, because every installed copy's updater (`updates.ZIP_ROOT`) refuses a zip without it, Windows installs included. `release` uploads all three files; it stays a Windows-only command (Inno Setup). The README and `START HERE.txt` tell Mac users to drag the folder into **Applications**: Desktop and Documents are often iCloud-synced, and the `.venv` setup creates there would be uploaded or evicted by Optimize Storage. Mac work is done on a MacBook checkout of the same repo and tested there; push it, `git pull` on Windows, then release.

## Data layout

**Two folders, kept apart** (`config.py`): the **app folder** (`PROJECT_ROOT`) is the software and
holds nothing personal, so it can be replaced or published; the **data folder** (`DATA_DIR`,
`~/DepopSeller`, overridden by `DEPOP_SELLER_DATA` or `data_dir` in the per-machine
`machine_config_file()`) holds everything of the seller's. That split is the whole reason moving to
another computer is one copy - never put seller data back in the app folder.
`migrate_into_data_dir()` moves an older install's `product_image`, `depop_seller.db`,
`description_style.md`, `style_history` and `.env` across once (called from `cli.main`, never
overwrites, a rename when both are on one drive), and `load_api_key` still reads the app folder's
`.env` as a fallback.

```
<data dir>/                       # ~/DepopSeller - the one folder a seller carries between machines
  product_image/<batch>/          # any safe folder name: a date, "Autumn knits", ...
    raw_image/      input HEIC — the app only ever *adds* files here (upload / import); existing photos are never modified, moved or deleted
    thumbs/         512 px JPEG cache (rebuilt on demand if missing)
    cache/          scan.json + cached model responses (generated)
    manifest.csv    one row per photo; the human-reviewed truth
    manifest.bak.csv  previous version, written by every save
    sort_image/     optional export: <item_id>_<photo_no>.jpg + manifest.csv — always copied, never moved
  depop_seller.db                 # local SQLite: items + photos per batch
  description_style.md            # the seller's own style, started from the app's template
  style_history/                  # previous versions of it
  .env                            # ANTHROPIC_API_KEY

<app folder>/                     # the software: code, launchers, the extension, the style template
```

## Step 1 pipeline

```
.venv\Scripts\python.exe -m depop_seller check                 # env, batches, API key status
.venv\Scripts\python.exe -m depop_seller sort <batch>          # scan -> group (API) -> manifest.csv
.venv\Scripts\python.exe -m depop_seller review <batch>        # drag-and-drop review UI in the browser; Approve = apply
.venv\Scripts\python.exe -m depop_seller sort <batch> --apply  # apply from the CLI instead: sort_image/ + DB
```

- `sort` reuses an existing `manifest.csv` (human edits are sacred; it only refreshes derived columns); `--regroup` re-runs the engine after backing the old manifest up as `manifest.bak-*.csv`. `--limit N` for cheap API testing (with `--regroup`).
- Grouping engine (`group.py`, orchestrated by `group_batch`): Anthropic API, `claude-opus-5` by default (`--model`, `--effort`). (1) Windowed pass: 8 thumbnails plus 2 context photos from the previous window, time gaps as text hints, structured output via `client.messages.parse(output_format=WindowResult)`; the model also returns `is_product` (false -> skipped). (2) Merge pass (`find_duplicates`): a catalog of every item's cover at 384 px (prompt-cached via `cache_control` on the last catalog block, chunks of 80) plus 8 query items per call; `Match` results with `high` confidence are merged by `apply_matches` (later item's photos appended), `medium` ones are written to `cache/suggestions.json` for the review page. Responses are cached in `cache/group/` and `cache/match/`; `PROMPT_VERSION` / `MATCH_PROMPT_VERSION` are part of the keys. The engine writes `cache/proposal_windows.csv` and `cache/proposal.csv` for `learn`. `--engine local` (time gap + colour distance) is the offline fallback and over-splits.
- `learn.py` / `depop learn <batch>` scores a proposal against the reviewed manifest (boundary precision/recall, stitched items, moves, drops) and `--test-merge-pass` re-runs and scores the merge pass. Measured on a real 438-photo batch: windowed pass 100%/100%; merge pass found 7/7 reviewer merges + 38 correct ones the reviewer missed (one medium false alarm: a bag that was a styling prop in another item's photos). Cost: merge pass ~$2 on Opus for 101 items. There is no fine-tuning: improving the engine means editing prompts and re-scoring with `learn`.
- Manifest model (`manifest.py`) is explicit: `item_id`, `photo_no`, `skip`, `deleted`, `view` per row. `deleted` = not for sale (implies skip; shown in the UI's Deleted section, restorable by drag; `raw_image/` is never touched). `unused()` excludes deleted rows. `normalize()` renumbers items densely by first photo and photos within each item, so by hand you just type the item number a photo belongs to (any unused number starts a new item). Skipped photos have item 0. Photo 1 of an item is Depop's cover; views are front/back/side/label/detail/flaw/other (Depop's slot order) and drive the UI's Auto-arrange. **The photo order (`photo_no`) is chosen by the reviewer and is sacred**: nothing downstream may re-sort it — `sort` (reuse path), `--apply`, the DB, `sort_image` names and the future Depop upload all follow `photo_no` exactly. In the UI only the explicit Auto-arrange buttons reorder (the global one asks for confirmation); Trim to 8 removes photos but keeps the remaining order.
- Review UI (`review.py` + `static/review.html`): stdlib `ThreadingHTTPServer` on 127.0.0.1, one `ReviewServer` holding a `ReviewSession` per batch; every batch route takes `?batch=`. Routes: `/batches`, `/state`, `/save`, `/group` + `/group/status` (scan + Claude grouping in a background thread, for batches without a manifest — the page shows a "Group with Claude (about $x)" panel using `group.COST_PER_PHOTO`), `/apply` + `/apply/status`, `/thumbs/<file>` and `/large/<file>` (both rebuilt from the original on first request - into `thumbs/` and `cache/large/` - so a batch folder copied from another computer, or one trimmed to save space, still shows its photos instead of broken tiles). Vanilla-JS page: batch dropdown in the header, HTML5 drag and drop, per-card Merge into #, Auto-arrange, Delete item, Trim to 8 (burst duplicates and lowest-priority views go to Unused), a "Possible re-shoots" panel fed by `/suggestions` (Merge / Not the same → `/suggestions/dismiss`), Unused bin and a Delete drop zone (Deleted section at the bottom), a ✕ on every tile (delete) / ↩ in the Deleted section (restore to Unused), a lightbox on image click (arrow keys, Esc, Delete/Unused buttons), Save (writes manifest.csv + manifest.bak.csv; payload = items / unused / deleted / views), Approve (apply, polled). `save()` validates the whole payload before mutating rows and refuses (409) when manifest.csv changed on disk since the session loaded it; `ReviewServer.session()` reloads a session whose manifest changed on disk. Synthetic mouse drags from browser automation don't start native DnD — test the handlers with dispatched `DragEvent`s and leave real drags to a human. `window.confirm` can be overridden in automation to click the paid buttons.
- **White Background** (`whitebg.py`, routes `/white`, `/white/status`, `/white/restore`, UI in `static/review.html`): **switched off since 1.1.x (owner's call, 2026-10-31: the cut-outs were not good enough to sell with)** by `config.WHITE_BACKGROUND = False`. The code, routes and tests stay; off means `state()` sends `white_enabled: false` and the Review page shows no checkboxes, no Select all, no selection bar and no help sentence; `start_white` refuses; and `large_image` / `thumb_image` / `white_stamps` / `apply_batch` ignore `cache/white/` (cut-outs made under 1.1.0 stay on disk, unused, so originals are shown, uploaded to Depop and exported). `tests/test_whitebg.py` switches it on with an autouse fixture and `test_switched_off_the_app_hides_it_refuses_it_and_shows_originals` pins the off state. `onnxruntime` stays a dependency on purpose: removing it changes `project.dependencies`, which makes the in-app updater refuse installed copies and send them to a new installer. To bring the feature back, set the flag to True and restore the README lines. As built: every photo tile on the Review page has a checkbox (plus **Select all** on an item card); the selection bar offers **White Background** and **Restore original**. It runs **locally** - `onnxruntime` (a normal dependency, except on Macs other than Apple silicon on macOS 14+, where no build exists: a `pyproject.toml` marker skips it there, `runtime_available()` is false and the page says which Macs can do it) plus the *BiRefNet tiny* model (224 MB, `BiRefNet-general-bb_swin_v1_tiny`; about 4 s a photo on a CPU), never the Anthropic API (it returns text, not masks). The model is fetched once from the pinned `MODEL_URL` (GitHub, prefix-checked, size-bounded, `MODEL_SHA256`-verified, `.part` file then rename) into `<machine config folder>/models/`, only after the page's confirm dialog sends `download: true`; the server refuses without it. Pipeline: 2048 px upright original (`original_large`) -> 1024 px network logits -> sigmoid -> full-size guided-filter refinement + soft threshold -> `drop_strays` (keeps the biggest region plus close or big-and-inside-the-frame ones; drops feet cut off by the frame, lamps, specks; pure numpy, no scipy/opencv) -> garment on pure white, cropped and centred on a 2048 px square with a 6% margin. Chosen after comparing three models on real photos: silueta (44 MB) deleted a graphic tee on a patterned blanket entirely and kept the blanket around another; isnet-general-use (179 MB) ate garments that fill the frame; BiRefNet tiny cut all of those out cleanly (and keeps bag handles and lace edges). Known limits: close-up shots (a collar, a label) are ambiguous by nature, and when the photographer's feet or a strip of the surface are joined to the garment in the mask they stay. The seller ticks photos by hand and can Restore. **Non-destructive:** results are `cache/white/<stem>.jpg` (+ `cache/white/thumbs/`); `ReviewSession.large_image` / `thumb_image` prefer them when they exist, so the Sell page, the Depop helper upload, description drafts and `apply_batch` (sort_image export) all use the white version automatically, and Restore just deletes the files. `raw_image/` and `manifest.csv` (photo order) are never touched, and no photo is renumbered. `state()` carries `white` (a millisecond stamp, 0 = none) per photo, which the page appends to image URLs. The job is a background thread like grouping (`white_state`, counted by `busy()` so closing the window does not stop it; refused during a batch rename); a photo the model finds no clothes in fails with a message rather than saving a blank square; replacing a photo (`replace=1` upload) drops its stale cut-out. Tests: `tests/test_whitebg.py` (fake mask function and fake `urlopen`; the real model is not needed). The installer's smoke test imports `onnxruntime` and `whitebg`; a release whose dependencies changed is refused by the in-app updater on installed copies and points to the new `DepopSellerSetup.exe`.
- Selling, preferred path (`chrome_extension/` + `static/sell.html`): a Manifest V3 extension the user loads unpacked. `sell_page.js` runs on 127.0.0.1:8765, marks `documentElement.dataset.depopSellerExt` and stores `{batch, item, server}` in `chrome.storage.local` on a `depop-seller:open` postMessage; the page then opens `https://www.depop.com/products/create/` in a new tab. `depop.js` runs on depop.com, polls for a pending job + the create page + `input[type=file]`, fetches `/sell/photos` (JSON of `{name, url}` in reviewer order, max 8; the server converts to 2048 px JPEGs first) and the images, builds a `DataTransfer`, sets `input.files` and dispatches input/change (one per slot if the input is not `multiple`), shows a banner, clears the job, POSTs status "opened". The server sends `Access-Control-Allow-Origin: *` and answers OPTIONS so depop.com can call it. This runs in the user's own logged-in Chrome — no automation flags — because Depop's bot protection 403-blocked the Playwright window on its second run (2026-09-19). Test the content script with the harness pattern in git history: inject it into `/sell/testform` with a `chrome.storage` shim.
- Descriptions (`describe.py`, routes `/sell/describe` + `/sell/describe/status`) run **only on the user's Claude subscription through the Claude Code CLI — the Anthropic API must never be used for descriptions** (user's rule: the API is for photo grouping only; the API engine was removed on 2026-09-20). `draft_description` builds one prompt (system rules + the whole `description_style.md` + the facts line + the paths of the cover and up to 3 label/detail/flaw close-ups from `cache/large/`, which the CLI reads itself with the Read tool) and `run_claude_code` runs the desktop app's bundled CLI (found by `find_claude_cli`: `DEPOP_CLAUDE_CLI`, PATH, `%LOCALAPPDATA%\Packages\Claude_*\LocalCache\Roaming\Claude\claude-code\<ver>\claude.exe` — the packaged app's real files; `%APPDATA%\Claude\...` is only visible inside the app's own processes) as `claude -p --output-format stream-json --verbose --allowedTools Read --max-turns 12 --model opus` with the whole prompt on **stdin** (command-line length limits; fed from a thread, stderr drained by a thread). **Billing guarantee, two layers:** (1) the CLI gets `subscription_env()` — the parent environment minus every `ANTHROPIC_*` variable (until 2026-09-20 `load_api_key()` exported the grouping key into `os.environ` via `load_dotenv`, the CLI inherited it and silently billed the API instead of the subscription — ~$0.66 lost; `load_api_key()` now reads `.env` with `dotenv_values` without exporting, and `group.py` passes `api_key=` explicitly); (2) the first `system/init` event's `apiKeySource` must be `none`, otherwise `BillingRefused` and `_kill_tree` (taskkill /T on Windows — a `.cmd` shim would survive `Popen.kill()`). `DraftResult.credential` records the source; `Draft` = text + title/brand/size/color/condition/measurements/category_hint/missing/tip, parsed from the `result` event (`_extract_json` handles fences); cost is None. The CLI has its own login separate from the desktop app: the user signs in once from Settings → **Sign in with Claude** (in the browser, see the Settings bullet); until then the CLI answers "Not logged in". `find_claude_cli` searches, in order: `DEPOP_CLAUDE_CLI`, PATH, the desktop app's bundle dirs per OS (`_bundle_dirs`: the packaged-app path on Windows, `~/Library/Application Support/Claude/claude-code` on macOS, where each version holds `<build>/claude.app/Contents/MacOS/claude` rather than a bare `claude` - `_cli_in` handles both), then standalone installs (`_standalone_paths`: `~/.claude/local`, homebrew, npm) - PATH is never relied on because an app launched from Finder or Explorer inherits a minimal one. `_kill_tree` uses `taskkill /T` on Windows and `killpg` elsewhere (the CLI gets `start_new_session=True`). `ReviewServer.start_describe(batch, item_ids, facts)` runs items sequentially in a thread, saves text + fields to the DB (`items.facts` / `items.measurements` added by `db._migrate`), state in `describe_state[batch][item]`, and `_log_draft` writes a readable `cache/drafts/item###_<ts>.txt` per draft. The Sell page has no engine choice and no cost figures; the card shows "Drafted with Claude Code". Note the CLI's `total_cost_usd` field is an estimate it always prints, not a charge. `/sell/photos` also returns `description`, and `depop.js` pastes it after the photos via `fillDescription`: tries textarea selectors, then visible `[contenteditable]` boxes (execCommand insertText, fallback textContent + InputEvent), then inputs; verifies the value took; the banner reports failure. Helper version is in the manifest (1.1) and mirrored as `HELPER_VERSION` in sell.html, which warns when Chrome still runs an older copy (unpacked extensions need a manual reload on chrome://extensions). Tested with a stub `.cmd` CLI speaking stream-json (`tests/test_claude_code_engine_parses_cli_envelope`, `test_claude_code_never_sees_the_api_key`). Gotcha that has now bitten twice: the Bash tool turns `\n` inside heredocs into real newlines - write files with escapes through the Write tool or build strings with chr(10). In a page's JavaScript a real newline inside a quoted string makes the whole `<script>` fail to parse, and the page then sits there with every status still reading "checking..." while the server answers fine; `test_every_page_script_has_no_string_broken_across_lines` catches that now. Test code has the same trap - build regex escapes with `chr(92)`.
- Sell page (`static/sell.html`, routes `/sell/state`, `/sell/item`, `/sell/reorder`): cards in manifest order with unlisted items first and listed ones under a "Listed on Depop" divider at the bottom (ticking Listed re-renders and moves the card); the red button is labelled just "Depop". Photo tiles are draggable **within their own item only** (regrouping stays on the review page): drop → `POST /sell/reorder?item=N {seqs:[...]}` → `ReviewSession.reorder_item` sets `photo_no`, writes manifest.csv + manifest.bak.csv through the same `_check_unchanged` (409) / `_write_manifest` helpers as `save()` (so an open review window with unsaved edits will get the 409 on its next Save — by design), and the page re-renders just that card from the response. `normalize()` orders items by their smallest `seq`, so reordering never renumbers items and the DB keeps the item's fields (same photo set). Clicking a tile opens a lightbox (thumb first, then `/large/`; arrows/Esc; "Make cover" = reorder with that photo first). Sell-state photos carry `seq` for this. Handlers are tested with dispatched `DragEvent`s in the browser (see the review-page note) and `test_sell_reorder_writes_manifest_and_keeps_item_fields`.
- Selling, fallback path (`listing.py`, routes `/sell`, `/sell/state`, `/sell/open`, `/sell/status`, `/sell/item`): `Lister` is a queue processed by one worker thread that owns a Playwright persistent context — the installed Google Chrome (`channel="chrome"`, falling back to msedge / bundled chromium) with its own profile in `.chrome-profile/` so the Depop login persists. A job converts the item's first 8 photos via `ReviewSession.large_image` (2048 px JPEGs in `cache/large/`), opens `https://www.depop.com/products/create/` in a new tab, waits up to 15 min for `input[type=file]` (login by the human), uploads all files at once when the input is `multiple` else one per slot, fills a textarea with the description if any, and leaves the tab open. **It never presses Post.** `db.sync_from_manifest` mirrors the manifest into the DB on every `/sell/state`, keeping status/description/depop_url per item (by photo set). `/sell/testform` is a stand-in form for smoke-testing the upload code without Depop. Playwright's sync API must stay on the worker thread. `sort --apply` / `sort_image` is now optional (export only).
- Hub / batches page (`static/hub.html`, the app's home): one card per batch with its cover (`GET /batches/cover`, a 512 px JPEG made on demand into `cache/cover-<stem>.jpg`), counts, `updated`, and the buttons **Add photos**, **Import folder…**, **Group with Claude (about $x)**, **Review**, **Sell**, **Rename**, **Open folder**. It finds the project by walking up, then the recorded path, then Spotlight (`mdfind` for `Depop Seller.app` outside `/AppTranslocation/` - a downloaded, unmoved app is run from a random read-only copy), then a folder picker. The whole script runs inside `main()` so an update can rewrite it while it runs (bash reads scripts as it goes); progress is `display notification`, failures are dialogs pointing at `~/Library/Logs/Depop Seller.log`. Rehearsed on a recipient-shaped copy (no `.venv`, no photos, no `.env`) - it installed and launched; remember that `setup.ps1` rewrites the Desktop shortcut, so re-run `make_desktop_icon.ps1` afterwards. **Gatekeeper is the one thing left**: an unsigned `.app` that arrived as a download is blocked until the user allows it in System Settings → Privacy & Security; copying the folder from a USB stick or a synced drive carries no quarantine and avoids it.
- **Windows installer** (`installer.py`, `installer/DepopSeller.iss`, built by `release`): `DepopSellerSetup.exe` (about 23 MB) installs per user - `PrivilegesRequired=lowest`, no administrator password - into `%LOCALAPPDATA%\Programs\Depop Seller` as `runtime\` (Python's official **embeddable** build for the release machine's exact Python, downloaded once from python.org into `build/`, with a `python3XX._pth` of `python3XX.zip`, `.`, `Lib\site-packages`, `..\app`, `import site` - so it ignores every other Python on the machine) and `app\` (the release zip unpacked - the folder the updater keeps current). Libraries are `pip install --target` with **every package of the build venv as a constraint**, so the bundle has exactly the versions the tests passed with. `smoke_test` imports everything from the staged runtime (and checks the modules came from the bundle) and starts the staged app's server, asks `/version`, then `/quit`; `check_path_lengths` fails the build if a file would pass 260 characters once installed (`MAX_INSIDE`: the anthropic SDK's longest compiled type is ~159). **The bundle must never name a folder of the release machine**: pip and Python write the full source path into every `.pyc`, and on Windows the home folder is the owner's real name, so `strip_build_paths` recompiles each `.pyc` with a path relative to the install folder before the smoke test (Python swaps in the real path on import, and the timestamps still match, so the files are used), the smoke test runs with `-B` so it adds none (the app's own `.pyc` are made on first launch), and `check_no_local_paths` refuses the build if any staged file still contains the home or project folder - either slash, the 8.3 short name, UTF-8 or UTF-16, any case (`test_the_bundle_never_names_a_folder_of_the_release_machine`). Start menu + Desktop icons run `runtime\pythonw.exe -m depop_seller hub` in `app\`; `[InstallDelete]` wipes both folders so an upgrade starts clean; `PrepareToInstall` and `InitializeUninstall` POST `/quit` to 127.0.0.1:8765 so an open copy lets go of its files. **Never change `AppId`** - it is how a newer installer upgrades instead of adding a second copy. Unsigned, so SmartScreen says "Windows protected your PC" once (More info → Run anyway); the README says so. Inno Setup 6 is on the release machine per-user (`%LOCALAPPDATA%\Programs\Inno Setup 6`, found by `find_iscc`, or `DEPOP_ISCC`). **Testing an installer on a working machine**: `/VERYSILENT /SUPPRESSMSGBOXES /desktopicon=no` (the icon would otherwise replace the developer's own `Depop Seller.lnk`), only with nothing on port 8765 (it would be closed), never into a deep folder (the 260 limit - a long temp folder is enough to break it), and uninstall afterwards with `unins000.exe /VERYSILENT`. - **Giving the app away**: Settings shows the project page link first (the page has the Download button); the zip is the fallback for no internet. **The zip** (`share.py`, `POST /settings/share`) writes `~/Desktop/Depop Seller <date>.zip` containing the project minus `SKIP_DIRS` (`.git`, `.venv`, `product_image`, `style_history`, `.chrome-profile`, `.claude`, caches, `*.egg-info`), minus `.db` / `.log` / `.pyc` / `.zip`, minus anything named `.env*`, plus a generated plain-language `START HERE.txt` (`GUIDE`; a copy that came out of a zip already holds one, so `_included` leaves the folder's copy out - but `is_shareable` still accepts it, since every release carries one; skipping it there once made the updater refuse every release, and `test_the_app_folder_is_the_release_zip_unpacked_with_one_guide` pins both). Modes are set explicitly (`_add` builds each `ZipInfo` with `create_system = 3` and `0o755` for `Contents/MacOS/*` and `*.sh`, `0o644` otherwise): **Windows has no executable bit**, so a plain `ZipFile.write` ships an app bundle whose executable cannot be run, and macOS reports that as "you need to install Rosetta" - nothing to do with architecture. `Info.plist` also sets `LSRequiresNativeExecution`. - **No console for the people using it** (they are not engineers; a terminal window reads as something being wrong). The Windows Desktop shortcut runs `.venv\Scripts\pythonw.exe -m depop_seller hub` - **pythonw has no console at all**, which also means `sys.stdout`/`sys.stderr` are `None` and any `print` would raise: `cli.windowless()` detects that (or `DEPOP_QUIET=1`, set by the macOS bundle) and `_log_to_file()` redirects both to `config.LOG_FILE` (`%LOCALAPPDATA%\Depop Seller\app.log`, `~/Library/Logs/Depop Seller.log`) before anything prints. Also: the bundle never opens Terminal, sets `DEPOP_QUIET=1`, logs to `~/Library/Logs`, and `Info.plist` sets **`LSMultipleInstancesAllowed`** because macOS otherwise just activates the running copy on a second double-click instead of reopening the window (with it, the second instance finds the port busy, opens the window and exits, like Windows). The sign-in `osascript` **must single-quote the CLI path** - it lives under "Application Support" - covered by `test_claude_sign_in_window_quotes_the_mac_path`. `setup.sh` clears `com.apple.quarantine` for copies that arrived as a ZIP.

- **Check for updates** (`updates.py`, Settings → Updates, routes `POST /updates/check`, `POST /updates/install`, `GET /updates/status`): `check()` asks `api.github.com/repos/doyoungp-dev/depop_seller/releases/latest` (stdlib `urllib`, User-Agent set, 20 s timeout) and never raises - 404 means nothing published yet, 403/429 rate limited, offline is a plain sentence. `/updates/install` re-asks GitHub itself (the download URL is never taken from the request) and runs `install()` in a thread, refused while `busy()`; an update in progress counts as busy, so closing the window cannot stop it half-way. `install()` touches the **app folder only**: the download must start with `DOWNLOAD_PREFIX` and stay under 50 MB, every zip member must sit under `depop_seller_app/`, contain no `..`, backslash, drive or absolute path, and pass `share.is_shareable` (so a release can never write `.venv`, `.git`, `.env*`, `product_image`, a `.db` or the seller's `description_style.md`), and it must carry a `__version__`. Only files whose bytes differ are written; each replaced file is copied first to `%LOCALAPPDATA%\Depop Seller\previous-version` (machine folder, not the data folder); then `finish()` reinstalls the package only if `project.dependencies` changed and proves the new code imports in a separate process of the same Python (`_app_python()`: the `.venv`'s, or the installer's runtime) - if anything fails, the old files are put back and new ones removed. ## Conventions

- Python: type hints, `pathlib`, `argparse` CLI, stdlib `logging`; small modules (`scan`, `group`, `manifest`, `review`, `apply`).
- Idempotent and safe: re-running never destroys data; `--apply` refuses to write into a non-empty `sort_image/` unless `--force`.
- Tests in `tests/` (pytest) use tiny synthetic images, never the real photos.
- Follow the Anthropic SDK patterns from the `claude-api` skill when touching `group.py` (no `budget_tokens`, no prefill; use `output_config` for structured output).
